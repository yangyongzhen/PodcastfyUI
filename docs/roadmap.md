# 后续路线：从播客音频到视频（L1–L4）

> 记录时间：2026-09-12。本文件是**计划**，记载尚未实现的能力；每档都给了可复现的验证命令与验收标准，便于随时复核、也便于换人接手。
> 与 `release-readiness.md` 的分工：那份管「上架前硬伤」，这份管「上架后的功能演进」。

## 为什么做

当前唯一产物是 mp3（双人对谈）。但播客的分发场景里，视频平台（B 站 / 视频号 / YouTube）的流量远大于音频订阅：一段「能看的音频」（封面 + 波形 + 对白字幕）比裸 mp3 更容易被点开与转发。

因此把「音频 → 视频」拆成四档，按投入从小到大排列，**每档独立可交付**，不做一次性大改造。核心判断：**素材全都在手**——对话稿（文本）、每行音频（`parts/NNNN.mp3`）、每行时长（`ffprobe` 可得），所以从 L1 到 L3 都不需要碰生成逻辑，纯粹是「多一个导出阶段」。

## 现状盘点（2026-09-12 实测）

| 能力 | 结论 | 复现命令 |
| --- | --- | --- |
| H.264 / H.265 编码 | ✅ 可用 | `ffmpeg -hide_banner -encoders \| grep -E ' (libx264\|libx265) '` |
| AAC 音频编码 | ✅ 可用 | `ffmpeg -hide_banner -encoders \| grep ' aac '` |
| mp4 封装 | ✅ 可用 | `ffmpeg -hide_banner -muxers \| grep -w mp4` |
| 波形 / 频谱滤镜 | ✅ 可用 | `ffmpeg -hide_banner -filters \| grep -E ' (showwaves\|showspectrum) '` |
| 字幕 / 文字滤镜 | ✅ 可用 | `ffmpeg -hide_banner -filters \| grep -E ' (subtitles\|ass\|drawtext) '` |
| 中文字体 | ⚠️ 系统仅 **1** 个中文字体，视频内中文必须显式指定字体文件 | `fc-list :lang=zh \| wc -l` |
| 代码现状 | 目前**无任何视频相关代码**（`extractor` 里的 YouTube 字幕抽取与本路线无关） | `grep -rniE 'mp4\|video' src-tauri/src src/routes` |
| 可行性样例 | ✅ 已用真实成品出片，见下节 | — |

### 复现样例（已实测跑通）

用真实端到端产出的 mp3（202.5 秒双人对谈）生成 20 秒波形视频：

```bash
ffmpeg -y -i /tmp/podcastfy-demo.mp3 \
  -filter_complex "[0:a]showwaves=s=1280x720:mode=cline:colors=cyan|white:rate=25,format=yuv420p[v]" \
  -map "[v]" -map 0:a -c:v libx264 -preset veryfast -t 20 -c:a aac -b:a 128k /tmp/demo-clip.mp4
# 实测产物：3,664,582 字节，h264 1280x720，20 秒（去掉 -t 20 即出全片）
```

这条命令就是 L2 的原型；L1 只需把滤镜换成静态图像输入。

## 分档路线

### L1 静态封面视频

- **效果**：封面图铺满画面 + 完整音频，输出 mp4，可直接上传视频平台。
- **实现**：`ffmpeg -loop 1 -i cover.png -i podcast.mp3 -c:v libx264 -tune stillimage -pix_fmt yuv420p -c:a aac -shortest out.mp4`。
- **依赖**：无新增，复用 `src-tauri/src/audio/mod.rs` 的 `find_ffmpeg()`。
- **成本**：小（半天级）。
- **验收**：任一已完成任务能导出 mp4，时长与音频一致、系统播放器可播、分辨率与音量无异常。
- **风险**：封面素材来源（需确认可用授权，或由应用内置生成一张纯色/渐变底图）。

### L2 波形 / 频谱可视化

- **效果**：画面随声音跳动（`showwaves` 声波或 `showspectrum` 频谱），比静止封面更像「播客视频」。
- **实现**：即上文复现样例；可再叠 `drawtext` 打上播客名与两位主持人名。
- **依赖**：无新增。
- **成本**：小，**建议与 L1 合并成同一个「导出视频」按钮**，用参数区分两种视觉风格。
- **验收**：导出耗时在可接受范围（1080p 下应远快于音频实时时长）；画面与音频同步、无掉帧卡顿。
- **风险**：长音频的编码时间与文件体积，需要给进度与取消（沿用现有四阶段进度机制）。

### L3 双人对白字幕

- **效果**：画面下方逐句出字幕，可按主持人在视觉上区分（人 1 靠左 / 人 2 靠右，或两色区分），成品像「带字幕的访谈视频」。
- **实现**（全程不需要碰生成逻辑）：
  1. **取每行时长**：管道本就把每行合成成独立 mp3（`parts/NNNN.mp3`），对每段跑 `ffprobe -v error -show_entries format=duration -of csv=p=0` 得到秒数；
  2. **累加出时间轴**：按顺序累加得到每句的起止时间，结合行文本与角色生成 SRT（或 ASS，便于按角色上色与左右定位）；
  3. **烧进画面**：`ffmpeg -i in.mp3 -i cover.png -vf "subtitles=out.ass:fontsdir=<字体目录>" ...`，可与 L2 波形滤镜叠加。
- **依赖**：无新增 crate（`ffprobe` 与 ffmpeg 同源，项目已在用）。
- **成本**：中（时间轴累加、ASS 样式、字体路径三处细节）。
- **验收**：随机抽 3 句字幕与音频对照，文字一致、时间偏差 ≤ ±0.3 秒；中文无方块/豆腐字；角色颜色与说话人对应无误。
- **风险**：
  - **台词转义**：文本里可能含 `<`、`>`、`&`、逗号、换行，直接拼进 SRT/ASS 会导致字幕错位甚至 ffmpeg 报错——必须走转义，**不要用字符串拼接**；
  - **行号必须与 `split_transcript()` 的结果对齐**（`src-tauri/src/queue/pipeline.rs`），不要另起一套切分逻辑，否则字幕与音频错位；
  - 中文字体：见「授权与依赖」一节。

### L4 动态双人形象（进阶，建议暂缓）

- **效果**：两位主持人的形象（头像/立绘）在说话时高亮或有轻微动作，接近 NotebookLM 那种「双人播客视频」。
- **实现**：两条路线可选——
  1. **ffmpeg 滤镜图**：`overlay` 立绘 + `enable='between(t,…)'` 按时间轴切换高亮，或加淡入淡出；产物是纯 mp4，无前端参与；
  2. **前端渲染**：任务卡片用 Canvas 播放渲染、`MediaRecorder` 导出；更灵活，但依赖 webview 能力，跨平台表现不一致。
- **依赖**：角色素材（**授权必须确认**）、更复杂的滤镜图；可能引入 `image` / `resvg` 之类 crate 做素材预处理。
- **成本**：**大**，属新功能级。建议等 L1–L3 被真实使用后再评估，不要现在动。
- **验收**：形象与说话人严格对应（不许错位）；长音频音画同步无漂移；导出文件被主流播放器与视频平台接受。
- **风险**：素材版权、渲染耗时（长音频可能数倍于实时）、跨平台编码差异。

## 授权与依赖（先看清楚，别踩坑）

| 事项 | 现状 / 结论 | 影响 |
| --- | --- | --- |
| ffmpeg | 项目决策为**不自带**（见 `release-readiness.md` 第 1 项），只做启动自检 | 视频导出继承同一前置，不新增安装负担 |
| libx264 | **GPL** 许可 | 若将来改为随包分发 ffmpeg，用 GPL 构建会让整个应用受 GPL 约束，与 Apache-2.0 口径冲突；应选 **LGPL 构建**，或改用 openh264 / 硬件编码 |
| 中文字体 | 系统仅 **1** 个中文字体 | 视频内中文需显式指定字体路径；若要跨机一致，随包带一份 **OFL** 字体（如 Noto Sans SC / 思源黑体）并注明授权 |
| 封面 / 角色素材 | 尚未确定 | 必须可商用，或由应用自绘（纯色、渐变、几何图形零授权风险） |
| 新增 crate | L1–L3 **无需**新增 | 仅 L4 可能引入 `image` / `resvg` |

## 落点与改动面（按最小改动评估）

- **后端**：新增 `src-tauri/src/video/mod.rs`，复用 `src-tauri/src/audio/mod.rs::find_ffmpeg()` 定位 ffmpeg；对外提供「导出视频」命令（风格参数 + 输出路径 + 进度回调）。
- **管道**：`src-tauri/src/queue/pipeline.rs` 增一个**可选第五阶段**（导出视频）；失败**不得**影响既有的 mp3 产物，进度沿用现有事件机制。
- **前端**：`src/routes/TaskCard.svelte` 加「导出视频」按钮 + 风格选择（封面 / 波形 / 字幕）；导出结果用现成的 `convertFileSrc`（`src/lib/api.ts`）在应用内预览播放。
- **命令与事件**：按 `docs/api.md` 既有风格补导出命令与进度事件。
- **文档**：同步更新 `docs/modules.md`、`docs/architecture.md`；某档做完后，把它从本文件移到「已完成」并补实测数据。

## 建议顺序

1. **L1 + L2 合并实现**（一个「导出视频」按钮、两种视觉风格）——成本最小，立刻有可分享产物；
2. 用真实成品跑一次验收，口径对照上文「复现样例」；
3. **L3 字幕**作为下一步主打特色（双人对白是这类播客的天然卖点，且时间轴与文本素材已在手）；
4. **L4 暂缓**，等前三档被真实使用后按需评估。

## 待拍板

- **画幅**：16:9 横版与 9:16 竖版（短视频平台）是否都要？两者封面与字幕排布需各做一套。
- **封面素材**：应用自绘（零授权风险），还是允许用户自选图片？
- **中文字体**：依赖系统字体，还是随包分发一份 OFL 字体（体积约 +5–10 MB）？
- **批量导出**：是否需要一次为多个已完成任务出片？
